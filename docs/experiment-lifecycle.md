# Experiment lifecycle

This document defines the lifecycle and transition rules for experiments generated by the NGI541 benchmark framework.

The lifecycle is designed to preserve partial results, support safe resume after interruption, and separate experiment execution from evidence acceptance.

## Lifecycle states

```text
CREATED
   ↓
PREPARING
   ↓
READY
   ↓
RUNNING
   ↓
ANALYZING
   ↓
COMPLETE
```

Exceptional terminal states:

```text
FAILED
ABORTED
```

A failure or abort never deletes the experiment directory.

Collected provenance, logs, raw attempts, and partial measurements remain available for forensic analysis.

## State meanings

### `CREATED`

The experiment identity and directory exist.

At minimum:

- experiment ID is allocated;
- `config/request.json` exists;
- `state.json` exists;
- `logs/framework.log` exists.

### `PREPARING`

The framework resolves configuration and prepares the execution environment.

Typical work includes:

- validating user input;
- applying defaults;
- producing `config/resolved.json`;
- preparing the environment adapter;
- discovering nodes;
- recording hardware and operating-system inventory;
- resolving source and dependency identities;
- building or locating binaries;
- fingerprinting binaries;
- validating workload prerequisites;
- running required correctness gates.

Failure during preparation transitions the experiment to `FAILED`.

### `READY`

All immutable pre-run metadata is complete.

Before entering `READY`, the framework must have created and validated:

```text
config/resolved.json
manifest.json
environment/**
provenance/**
execution/schedule.json
```

These artifacts become immutable at `READY`.

### `RUNNING`

Measured execution is in progress.

The runner consumes the immutable schedule in sequence.

Each execution attempt writes into a new append-only attempt directory.

Completed attempts are never overwritten.

### `ANALYZING`

Measured execution has ended and the framework generates processed results.

Typical outputs:

```text
processed/summary.csv
processed/statistics.json
figures/*.svg
README.md
```

Analysis reads preserved raw measurements rather than transient process output.

A failure during analysis transitions the experiment to `FAILED` while preserving all raw data.

### `COMPLETE`

Execution and analysis completed successfully.

`COMPLETE` means the experiment is available for review.

It does not mean that the result is accepted project evidence.

### `FAILED`

A non-user-requested failure prevented the current lifecycle stage from completing.

Examples:

- missing dependency;
- preparation failure;
- failed correctness gate;
- workload failure exceeding retry policy;
- invalid measurement output;
- analysis failure.

The failure reason must be recorded.

A failed experiment remains on disk and may be eligible for resume.

### `ABORTED`

Execution was intentionally stopped.

Already completed attempts remain preserved.

The experiment may later be resumed if its immutable metadata remains valid.

## Allowed transitions

```text
CREATED    → PREPARING
PREPARING  → READY
PREPARING  → FAILED

READY      → RUNNING
READY      → ABORTED

RUNNING    → ANALYZING
RUNNING    → FAILED
RUNNING    → ABORTED

ANALYZING  → COMPLETE
ANALYZING  → FAILED

FAILED     → PREPARING
FAILED     → RUNNING
FAILED     → ANALYZING

ABORTED    → RUNNING
```

Resume target depends on the latest successfully completed lifecycle boundary.

The orchestrator must validate immutable artifacts before resuming.

## Atomic state persistence

`state.json` must be updated atomically.

Recommended pattern:

```text
write state.json.tmp
flush and close
atomic rename → state.json
```

The framework must not update the active `state.json` by truncating it in place.

## Experiment creation

The orchestrator:

1. validates workload and environment identifiers;
2. generates an immutable experiment ID;
3. creates the common filesystem layout;
4. writes `config/request.json`;
5. writes initial `state.json`;
6. creates `logs/framework.log`;
7. transitions to `PREPARING`.

A pre-existing experiment directory must never be overwritten.

## Preparation

Preparation should:

1. load the environment adapter;
2. normalize the node topology;
3. capture node inventory;
4. resolve workload defaults;
5. resolve variants;
6. capture source and dependency identities;
7. build or validate runtime artifacts;
8. record binary fingerprints;
9. run correctness and preflight validation;
10. generate the complete execution schedule;
11. create `manifest.json`;
12. validate generated metadata;
13. transition to `READY`.

Measured execution must not start if a required correctness gate fails.

## Schedule generation

The complete schedule is generated before `RUNNING`.

For paired A/B comparison, ordering is balanced ahead of execution.

Example:

```text
pair 1: stock → ngi541-direct
pair 2: ngi541-direct → stock
pair 3: stock → ngi541-direct
pair 4: ngi541-direct → stock
```

The runner executes the stored schedule and does not choose comparison order dynamically.

If randomized ordering is added later, the seed must be recorded.

## Run execution

Every schedule entry has a stable `run_id`.

First attempt:

```text
raw/runs/<run-id>/attempt-01/
```

Retry:

```text
raw/runs/<run-id>/attempt-02/
```

Earlier attempts remain unchanged.

An attempt is finalized only after its `measurement.json`, `stdout.log`, and `stderr.log` have been written.

## Measurement validity

Process success and measurement validity are distinct.

A process may return zero and still produce invalid or incomplete output.

Every measurement therefore records:

```json
{
  "execution": {
    "exit_code": 0,
    "valid": true,
    "failure": null
  }
}
```

Invalid attempts remain part of the raw record.

## Retry policy

Retry policy belongs to resolved configuration.

Retries are append-only and finite.

The framework records:

- the original attempt;
- failure reason;
- retry attempts;
- which attempt was selected for analysis.

The framework must never retry indefinitely.

## Resume semantics

`resume` acts on an existing experiment ID.

The orchestrator reads:

```text
state.json
manifest.json
execution/schedule.json
raw/runs/**
```

and determines the next valid action.

Typical behavior:

- preparation failure before `READY`: repeat preparation after validation;
- interruption during `RUNNING`: continue from the first run without a valid accepted attempt;
- failure during `ANALYZING`: regenerate processed outputs from raw data;
- abort during `RUNNING`: continue schedule execution.

Already valid raw attempts must not be rerun unless explicit policy requires it.

## Analysis

Analysis reads:

- immutable schedule;
- raw attempt records;
- explicit attempt-selection rules;
- analysis configuration.

It produces regenerable outputs.

`statistics.json` should identify:

- input run IDs;
- selected attempts;
- excluded attempts and reasons;
- summary statistics;
- comparison method;
- analysis implementation revision.

## Completion

The experiment transitions to `COMPLETE` only when:

- execution completion criteria are satisfied;
- required raw measurements exist;
- analysis completes;
- processed outputs pass structural validation;
- the generated experiment README can be produced.

A `COMPLETE` experiment is eligible to become an evidence candidate.

## Evidence lifecycle

Evidence has a separate lifecycle:

```text
COMPLETE experiment
        ↓
candidate generation
        ↓
review
        ↓
explicit promotion
        ↓
accepted evidence
```

The orchestrator may generate a candidate automatically or on request.

It must not automatically mark a performance claim as accepted.

Candidate location:

```text
evidence/candidates/<experiment-id>/
```

Accepted evidence remains curated under a stable project-facing identifier such as:

```text
evidence/performance/<canonical-evidence-id>/
```

## Failure preservation

On failure, the framework must retain all material collected so far, including:

- request configuration;
- resolved configuration if available;
- current state;
- framework log;
- environment information;
- provenance;
- execution schedule if generated;
- completed raw attempts;
- failure reason.

## Portability requirement

Lifecycle semantics must not depend on the environment adapter.

The same lifecycle applies to:

```text
local
baremetal
cloudlab
```

CloudLab may provision systems differently, but after node preparation it enters the same experiment lifecycle and emits the same experiment ABI.

## Historical C2.1 relationship

The frozen `c2.1-local-http3` experiment predates this lifecycle contract.

It remains historical evidence and must not be rewritten to look as though it was originally produced by R5.

Future R5 experiments must satisfy this lifecycle natively.
